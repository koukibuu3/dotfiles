# レビュー結果 → HTML レポート

直前のレビュー結果を、そのまま貼って共有できる **単体 HTML**（外部依存なし・CSS インライン）に整形する。

## 0. 大原則

- **レビューをやり直さない／指摘を増やさない。** 会話にある指摘だけを整形する。整形の過程で新しい問題を思いついても、このスキルの出力には入れない（別途テキストで伝える）。
- **指摘を薄めない。** 重要度・条件・ファイルパスは会話の内容をそのまま引き継ぐ。
- **日本語で書く。** 見出し・バッジ・本文すべて日本語。
- 会話にレビュー結果が無い場合のみ、先に対象（PR 番号・ブランチ・差分）を確認してレビューを実施し、そのうえで整形する。

## 1. 手順

1. **会話からレビュー結果を回収する。** 指摘・良い点・総評・確認したファイルパス・CI 状況を洗い出す。
2. **各指摘に重要度を割り当てる**（§2）。会話中で「高」「nit」等を既に明示していればそれに従う。
3. **`assets/template.html` を読み、プレースホルダを差し替えて 1 ファイルに組み立てる**（§3・§4）。テンプレートの CSS は変更しない（レポート間で見た目を揃えるため）。
4. **スクラッチパッドに書き出す。** ファイル名は `pr<番号>-review.html`、PR が無ければ `<ブランチ名>-review.html`。ユーザーのリポジトリ内には置かない。
5. **`SendUserFile` で `display: "render"` として渡す。** キャプションは 1 行。
6. **チャット側には構成の要約のみ書く。** HTML の中身を再掲しない。最後に `open <パス>` の bash ブロックと、「スクラッチパッド配下なので残すならコピーを」の一文を添える。

## 2. 重要度の割り当て

| バッジ | class | 使う場面 |
| --- | --- | --- |
| `高 / 要確認` | `high` | 本番影響・データ不整合・権限漏れ・リリース手順への依存。マージ前に必ず解消／確認が要るもの |
| `中` | `mid` | 実装は動くが設計・ロジックとして問題がある。別チケット化でも可なもの |
| `低` | `low` | ドキュメント齟齬、テスト不足、軽微な挙動差 |
| `nit` | `low` | 好みの範囲。直さなくてよいと明言できるもの |
| `プロセス` | `info` | コードではなく進め方の話（差分の作り方、コミット分割、レビュー負荷） |
| `GOOD` | `good` | 良い点。**必ず 1 件以上入れる**。無理に褒めず、実際に確認できた設計判断を書く |

サマリの件数バッジは 4 枠。`高 / 中 / 低+nit / プロセス` を基本とし、該当 0 件のカテゴリも 0 として表示する。

## 3. プレースホルダの埋め方

| プレースホルダ | 内容 |
| --- | --- |
| `{{TITLE}}` | `<title>` 用。`PR #7370 レビュー指摘事項 — <PRタイトル>` |
| `{{EYEBROW}}` | 小見出しラベル。例: `CODE REVIEW / QAST` |
| `{{H1}}` | `<a href="<PR URL>">PR #7370 — <PRタイトル></a>`。PR が無ければリンクなしのブランチ名 |
| `{{META}}` | チケット ID ／ ブランチ → ベース ／ 変更規模 ／ CI 状況。`<b>` で強調、`／` 区切り |
| `{{SUMMARY_STATS}}` | `.stat` ブロック 4 個（§4.1） |
| `{{FINDINGS}}` | `.item` ブロックを重要度の高い順に列挙（§4.2） |
| `{{GOOD_POINTS}}` | `.item good` ブロック（§4.3） |
| `{{EXTRA_SECTION}}` | 任意。整理表など（§4.4）。不要なら空文字 |
| `{{VERDICT}}` | `<p>` 2〜3 本（§4.5） |
| `{{FOOTER}}` | 何を確認した結果か 1 行。例: `生成: PR #7370 のレビュー結果まとめ（差分・CI・周辺コードの残存参照 grep まで確認）` |

## 4. 各ブロックの型

### 4.1 サマリ

```html
<div class="stat high"><div class="n">1</div><div class="l">高 / 要確認</div></div>
<div class="stat mid"><div class="n">1</div><div class="l">中</div></div>
<div class="stat low"><div class="n">3</div><div class="l">低 / nit</div></div>
<div class="stat info"><div class="n">1</div><div class="l">プロセス</div></div>
```

### 4.2 指摘 1 件

タイトルには **通し番号を付ける**（チャットで「指摘 1」と参照できるようにするため）。

```html
<div class="item high">
  <div class="head">
    <span class="badge high">高 / 要確認</span>
    <span class="title">1. 一文で言い切る見出し</span>
  </div>
  <p>何が起きるかを先に書く。原因の説明は後。</p>
  <div class="path">apps/.../target-file.ts:39</div>
  <div class="why"><b>提案：</b>どう対処するか。1〜2 文。</div>
  <pre><code>SELECT COUNT(*) FROM question WHERE groups_id = -1;</code></pre>
  <p class="note">※ 補足・除外条件</p>
</div>
```

使う要素の判断:

- `.path` — 該当箇所が特定できるとき。`ファイルパス:行` 形式。複数なら `.path` を並べる
- `.why` — **対処方針があるときだけ。** 「こうしてほしい」が無い指摘には付けない
- `<pre>` — 実行できるコマンド／クエリ／最小コードがあるとき。長い引用はしない（10 行以内）
- `.note` — 「これは本 PR 以前からの問題」「表示上の影響はない」など、指摘を正しく値切る情報

### 4.3 良い点

```html
<div class="item good">
  <div class="head">
    <span class="badge good">GOOD</span>
    <span class="title">後方互換の設計が正しく成立している</span>
  </div>
  <p>何をどう確認して成立していると言えるのか、根拠まで書く。</p>
</div>
```

### 4.4 任意セクション

大規模な削除・移行・リファクタで「どこを触ってどこを残したか」が要点になる場合は、`<h2>` + `<table>` を 1 つ足す。それ以外では入れない。

```html
<h2>削除範囲の整理</h2>
<table>
  <tr><th style="width:22%">レイヤ</th><th>内容</th></tr>
  <tr><td>フロント</td><td>...</td></tr>
</table>
```

### 4.5 総評

- 1 本目: 全体評価（ブロッカーの有無を明言する）
- 2 本目: **approve の条件を 1 つに絞って書く。** 「指摘 1 を手順として固定できれば approve」のように、読んだ人が次に何をすればいいか分かる形にする
- ブロッカーがある場合は条件ではなく「修正が必要な項目」として列挙する

```html
<p>方針・網羅性・後方互換の設計はいずれも妥当で、<strong>実装面のブロッカーはありません</strong>。</p>
<p>マージ前に <strong>指摘 1（...）</strong> を手順として固定できれば approve でよいと考えます。</p>
```

## 5. やらないこと

- CSS の書き換え・色の追加（レポート間の一貫性が崩れる）
- `<script>` の埋め込み（貼り付け先で動かないうえ、単に不要）
- 画像・外部フォント・CDN の参照（単体で開けなくなる）
- リポジトリ内へのファイル出力（レビュー成果物はコミット対象ではない）
- チャット本文への HTML 全文の再掲
